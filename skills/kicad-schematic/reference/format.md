# Формат `.kicad_sch` — то, что выяснено на практике

KiCad 10.0.4, версия формата `20260306`. Всё ниже проверено генерацией и
открытием файла, а не взято из документации: документация формата отстаёт,
а KiCad на ошибку отвечает одной фразой «Не удалось загрузить схему» без
номера строки.

## Скелет файла

```
(kicad_sch
	(version 20260306)
	(generator "schlib")
	(generator_version "10.0")
	(uuid "...")                     ; идентификатор ЛИСТА
	(paper "A4")
	(title_block (title "...") (rev "A") (company "..."))
	(lib_symbols ...)                ; определения всех использованных символов
	... элементы листа ...
	(sheet_instances (path "/" (page "1")))   ; ТОЛЬКО в корневом листе
	(embedded_fonts no)
)
```

Минимальный рабочий файл — 232 байта, его можно взять из
`/usr/share/kicad/template/EuroCard160mmX100mm/EuroCard160mmX100mm.kicad_sch`
и использовать как эталон при отладке.

## Ловушка № 1 — под-юниты символов

Определение символа втягивается из библиотеки и переименовывается в `Lib:Name`.
**Переименовывается только заголовок.** Вложенные под-юниты остаются как есть:

```
(symbol "Device:C"          ; <- переименован
	(symbol "C_0_1" ...)    ; <- НЕ трогать
	(symbol "C_1_1" ...)    ; <- НЕ трогать
)
```

Если написать `(symbol "Device:C_0_1")`, файл перестаёт открываться — молча,
без указания места. Это первое, что надо проверять, если файл не грузится.

## Ловушка № 2 — ссылки символов питания

Каждый `power:GND` — полноценный символ со ссылкой `#PWRxxx`. Если два листа
независимо начнут нумерацию с нуля, в проекте окажутся два `#PWR001`, и KiCad
при экспорте нетлиста скажет «схема содержит ошибки обозначения» — а нетлист
будет пустым. Нумерация обязана быть сквозной по всему проекту.

## Ловушка № 3 — путь инстанса

Каждый символ несёт блок `instances`, где записана его ссылка **для конкретного
места в иерархии**:

```
(instances
	(project "имя_проекта"          ; обязано совпадать с именем .kicad_pro
		(path "/<uuid корневого листа>/<uuid прямоугольника листа>"
			(reference "R1")
			(unit 1)
		)
	)
)
```

- В корневом листе путь короткий: `/<uuid корневого листа>`.
- В дочернем — `/<uuid корня>/<uuid ПРЯМОУГОЛЬНИКА листа>`. Именно прямоугольника
  на родительском листе, не самого файла. Один и тот же файл, вставленный дважды,
  даёт два пути и две разные ссылки — так в KiCad делают повторяющиеся каналы.

## Координаты и выводы

Ось Y на листе направлена **вниз**, в определении символа — **вверх**.
Поэтому координата вывода на листе получается инверсией Y и поворотом:

| Угол | Смещение вывода |
|---|---|
| 0 | `(+x, -y)` |
| 90 | `(-y, -x)` |
| 180 | `(-x, +y)` |
| 270 | `(+y, +x)` |

Порядок такой: сначала поворот против часовой стрелки в системе координат
символа, затем инверсия Y.

**Это место обязано проверяться машиной, а не глазом.** Формула для 90° может
быть перепутана с 270°, файл при этом открывается, схема рисуется, символ стоит
правильно — и только провода молча не попадают в выводы. Такая ошибка здесь
однажды и была. Ловится она так: символы ставятся под всеми четырьмя углами
**без единого провода**, а затем из отчёта ERC вынимаются координаты, которые
KiCad сам печатает для неподключённых выводов, и сравниваются с расчётом.

```bash
python3 scripts/selftest.py     # сверяет 48 выводов пяти символов
```

Прогонять после любой правки `pin_xy`, `label_positions` или `symbol_bbox`.

Сетка — 1,27 мм. Провод, не попавший в вывод, соединения не образует, и на
глаз это неразличимо; поэтому координаты выводов берутся расчётом, а не рулеткой.

## Иерархия

**На родительском листе** — прямоугольник:

```
(sheet
	(at X Y) (size W H)
	(uuid "...")
	(property "Sheetname" "Питание" ...)
	(property "Sheetfile" "power.kicad_sch" ...)
	(pin "VBAT" input (at X Y 180) (effects ...) (uuid "..."))
	(instances (project "имя" (path "/<uuid корня>" (page "2"))))
)
```

**В дочернем листе** — парная метка:

```
(hierarchical_label "VBAT" (shape input) (at X Y 180) (effects ...) (uuid "..."))
```

Имена обязаны совпадать посимвольно. Не совпали — KiCad считает это разными
цепями, ошибки не выдаёт, и блок просто оказывается ни к чему не подключён.
`Project.check()` сверяет их до записи файла.

Дочерний лист `sheet_instances` **не содержит** — он есть только в корне и
перечисляет все страницы:

```
(sheet_instances
	(path "/" (page "1"))
	(path "/<uuid прямоугольника>" (page "2"))
)
```

## Метки: какую выбрать

| Тип | Область действия | Когда |
|---|---|---|
| `label` | один лист | локальная цепь: `SPI_SCK` внутри блока |
| `global_label` | весь проект | питание и общие шины: `VBAT`, `+3V3` |
| `hierarchical_label` | лист + его вывод наверх | явный интерфейс блока |

Иерархические метки строже и читаемее: интерфейс блока виден на верхнем листе
целиком. Глобальные удобнее для питания, которое нужно везде и которое нет
смысла протаскивать выводом через каждый лист.

## Проверка результата

```bash
kicad-cli sch erc --severity-all --output erc.rpt проект.kicad_sch
kicad-cli sch export netlist --output net.net проект.kicad_sch   # цепи собрались?
kicad-cli sch export svg --output ./img проект.kicad_sch         # как выглядит?
kicad-cli sch export bom --output bom.csv проект.kicad_sch       # штатный BOM
```

Экспорт нетлиста — лучшая проверка иерархии: если цепь `+3V3` содержит выводы
деталей с разных листов, значит листы действительно связаны.
